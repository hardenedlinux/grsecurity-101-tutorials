# OS exploit mitigations: a comparative history

**Scope.** Memory safety, control flow, isolation, and exploit mitigation on Windows, vanilla Linux (mainline kernel plus the glibc/GCC/Clang toolchain and typical distro defaults), OpenBSD, and PaX/grsecurity. Android, macOS/iOS, FreeBSD/HardenedBSD, Solaris, and compiler mitigations are included where they pioneered something the others later copied.

**As of.** 17 October 2026. A date is exact when a release note, man page, or named patch pins it. Years marked **by** or **~** are only a bound. Where two independent sources disagree and the document says so in the row, that disagreement is the finding, and the row names both.

**How to read the dates.** "Created" is the first design or shipping implementation, not the first academic ancestor. "Adopted" is the first release where the feature exists on that platform. Default-on is called out separately, because a merged config symbol is not a mitigation.

**Vanilla Linux** means mainline plus what Ubuntu, Debian, and Fedora actually enable. A Red Hat-only patch (Exec Shield) is not mainline. A KSPP-recommended config is not a distro default.

PaX and grsecurity were developed separately and shipped together. **PaX** (PaX Team, 2000) is the exploit-mitigation research line. Wikipedia dates the first release 1 October 2000, from an infobox with no cited source. The oldest dated PaX artifact found is `pageexec.old.txt`, 16 November 2000. **grsecurity** (Brad Spengler, from about 2001; one page states both "16 years" and "since 2001") is the patch set that includes PaX, plus RBAC, chroot hardening, and infoleak closure. Public patches stopped on **26 April 2017**. The commercial tree continues. The download page re-read on **16 October 2026** lists stable trees **6.6.158** (`grsecurity-3.1-6.6.158-202610151448.patch`) and **6.18.56** (`grsecurity-3.1-6.18.56-202610151451.patch`), both stamped 10/15/26, plus a **7.1.13** beta (`grsecurity-3.1-7.1.13-202610151453.patch`). Treat the per-patch date as volatile and the version as the fact. The 6.18 line is marked supported at least through Q4 2028. The page's 6.6 row still reads "at least Q4 2026", which is itself stale: LWN, 25 Feb 2026, gives the upstream line as 6.6 through the end of 2027 and 6.12 and 6.18 through the end of 2028, and grsecurity has not updated that row. **Linux 6.18.0 was released 30 November 2025** and 6.18.1 was committed 12 December 2025. The earlier "6.18 chosen as next stable tree on 3 December 2025" date could not be sourced, and 6.18 did not become longterm when it was released. The historical public users were Hardened Gentoo for most of the project's life, and Alpine until the public patches ended.

| **NX / DEP / W^X / PAGEEXEC** (also XD, XN) | Hardware and tagged-machine precedents are much older (SPARC non-executable stacks via `noexec_user_stack` in Solaris 2.6, **August 1997**, but **disabled by default** and requiring an `/etc/system` edit). | **PaX MPROTECT** (strict W^X policy) | **PaX Team, 2000**, the same year as PAGEEXEC. Their own LATINOWARE 2012 deck says "MPROTECT: runtime code generation control (in 2000)". The nearest dated primary artifact is `pageexec.old.txt`, 16 Nov 2000. A cited "secondary chronology" dating the first incarnation to November 2000 could not be identified in this pass. The design note file is dated 4 November 2003, which is the document, not the feature. No new executable anonymous mappings, no W+X file mappings, and `mprotect` cannot add execute to a writable mapping or write to an executable one | Closest product analogue is **ACG** (Arbitrary Code Guard), **opt-in per process** (Edge and some system processes). | **Memory sealing** (`mseal`, `mimmutable`) | **OpenBSD first.** `mimmutable(2)` was implemented **4 Dec 2022** and shipped in **7.3** (10 Apr 2023). **Linux `mseal()` was merged for 6.10** (2024) and is explicitly patterned on it; the in-tree documentation cites `man.openbsd.org/mimmutable.2` and says the idea came from **Stephen Röttger's V8 CFI** work, with Chrome on ChromeOS named as the first intended user | No equivalent call. ACG stops new executable pages from appearing; it does not stop an already-mapped region being made writable afterwards | **`mseal()` in Linux 6.10** (2024). **glibc 2.43** (announced 23 January 2026) ships **only the wrapper**, not a loader policy: its `NEWS` says "On Linux, the mseal function has been added. It allows for sealing memory mappings to prevent further changes during process execution, such as changes to protection permissions, unmapping, relocation to another location, or shrinking the size," and `sysdeps/unix/sysv/linux/syscalls.list` gained the syscall. **This document previously said glibc 2.43 "ships the function and uses it", sealing the main binary, dependencies, preloads, the vDSO and `RTLD_NODELETE` libraries under a `glibc.rtld.seal` tunable with 0/1/2 semantics. That is wrong, and it was wrong twice over: there is no `rtld.seal` entry in glibc 2.43's `elf/dl-tunables.list` (its `rtld` tunables are `nns`, `optional_static_tls`, `enable_secure`, `execstack`, `dynamic_sort`), `grep -rn 'mseal or rtld.seal' glibc-2.43/elf/` returns nothing, and glibc 2.44, the current release, has no `seal` entry either.** The loader-sealing work is an unmerged series — Jeff Xu and Adhemerval Zanella, "[PATCH v6 0/9] Add support for memory sealing", libc-alpha, 10 Oct 2025, still asking "Could we merge this patch to main glibc?" The LWN article of 12 June 2024 that describes the `glibc.rtld.seal` proposal was reporting the plan, not the release, and this document collapsed the two | **Origin, and the stronger form.** OpenBSD marks the main program, `ld.so`, the main stack, load-time shared libraries and `dlopen`ed libraries mapped without `RTLD_NODELETE` immutable **automatically at program load**, per the 7.3 release notes: "Most of the program static address space is now automatically immutable". **This document said "at mount time" in two places, which is wrong** — it confuses load/exec time with the `wxallowed` mount option, which is about W^X, not immutability. `mimmutable(2)` remains the per-call manual escape hatch | No. MPROTECT constrains what may be created; sealing constrains what may be *changed* afterwards. They are complementary, not competing | Stop a write primitive from flipping the permissions of a mapping it did not have to touch, or from unmapping and re-mapping somewhere executable | **Not immutability, and the kernel says so.** `Documentation/userspace-api/mseal.rst` lists the ways a read-only mapping can still be written, quoting Jann Horn: `/proc/self/mem` with `FOLL_FORCE`, `ptrace` `PTRACE_POKETEXT`, and userfaultfd. **The section this document quoted by name, "mseal doesn't block", first appears in v6.12** — at v6.10, the version that shipped `mseal()`, the equivalent text sits under a heading "Additional notes" and does not mention `FOLL_FORCE`; `FOLL_FORCE` and the "doesn't block" wording are a v6.12 addition, so both are correct of current master and not of the 6.10 document this row cites. Sealing is also **one-way for the life of the process**, it must not be applied to memory the allocator will recycle, and it only binds mappings that were never writable to begin with. **The proposed `glibc.rtld.seal=1` would ignore a failure to seal and only `2` would kill the process, and the proposal would seal after RELRO, so it would not by itself have blocked the XZ backdoor — but that is a description of an unmerged patch series, not of any shipped glibc.** The OpenBSD model is stronger precisely because it is applied automatically at **load time** to the right mappings by default rather than per call at run time |
| **ASLR** (userspace) | Term coined and first implementation by the **PaX team, July 2001** (`RANDUSTACK`, `RANDMMAP`, `RANDEXEC`). Design in PaX `aslr.txt` | **Vista** (RTM Nov 2006, GA Jan 2007), opt-in per image via `/DYNAMICBASE`. Heap, stack, PEB, and TEB also randomized. **Windows 8** added high-entropy 64-bit ASLR (`/HIGHENTROPYVA`), **now sourced**: MSRC, 11 December 2013, "The ASLR implementation in Windows 8 takes full advantage of this opportunity by enabling high degrees of entropy for 64-bit applications", and Microsoft's `/HIGHENTROPYVA` page states the flag "is enabled by default for native applications when building with Visual Studio 2012 and beyond". Force-ASLR exists today as "Force randomization for images (Mandatory ASLR)"; the EMET lineage and the 1709 date are unconfirmed here | Weak mainline ASLR in **2.6.12** (17 Jun 2005). It was not a config option then: `randomize_va_space` is a hardcoded `int` in `kernel/sysctl.c`, and no `RANDOMIZE_VA_SPACE` symbol exists in any 2.6.12 `Kconfig`. `randomize_va_space=2` is the usual distro default. Exec ASLR requires PIE. Entropy improved, then **regressed in 5.18** (released **22 May 2022**, not the 8 May this document used to carry — 8 May 2022 is the `v5.18-rc6` date), and the mechanism is now confirmed in the kernel source rather than inferred: in 5.17 `thp_get_unmapped_area()` in `mm/huge_memory.c`, the 2 MiB-aligned path is gated behind `IS_DAX(...) && IS_ENABLED(CONFIG_FS_DAX_PMD)`; in 5.18 the DAX test is gone, so **every** file-backed mapping placed by ext4, ext2, xfs and fuse is aligned to `PMD_SIZE`, which is 2 MiB. Against the 28-bit `ARCH_MMAP_RND_BITS` that is log2(2 MiB / 4 KiB) = **9 bits** lost: 28 to 19 on 64-bit, and 8 to 0 on 32-bit. Binosi et al., ACM CCS 2024, confirmed the reduction without giving a bit count; the arithmetic and the Ubuntu/Arch/Fedora scope come from the "ASLRn't" write-up of 29 January 2024. **Ubuntu did raise the mmap entropy, and it is no longer Wikipedia's alone.** Launchpad #1983357, Thadeu Lima de Souza Cascardo, 19 October 2023: 32-bit library ASLR regressed because of upstream commit `1854bc6e2420` ("mm/readahead: Align file mappings for non-DAX"), the same PMD alignment as the 5.18 loss. On 26 October 2023 he wrote that he had "raised all values to the max, including the non-compat ones. That should recover some of the bits we lost due to this PMD alignment." The 6.5.0-25 changelog sets `ARCH_MMAP_RND_BITS` to the maximum, citing that bug; a measured jammy HWE kernel went from 28 on 6.5.0-21 to 32 on 6.5.0-25 (Launchpad #2056762, 13 March 2024). The fix is recorded as released in `linux 6.6.0-14.14` (noble), 4 January 2024. **32 does not undo the 9-bit alignment loss.** Against a 2 MiB alignment, 32 bits of offset is 23 bits of effective entropy, not the old 28. | **3.4** (1 Nov 2003): libraries load in a random order, and i386 maps them at somewhat randomized addresses. The innovations page calls this the first widely used default ASLR. The release note is narrower than a modern ASLR. Library relink of `libc`, `libcrypto`, and `ld.so` was implemented May 2016 and is default from **6.0**, expanded in **6.2**. **sshd is relinked at boot from 18 Jan 2023.** fork+exec so privileged children do not inherit a parent's layout | **Origin.** i386 design figures in the PaX doc: 24 bits of stack, 16 bits of mmap, 16 bits of exec. Also the first to argue that ASLR without crash reaction is brute-forceable, because `fork` preserves the layout | Make code and data addresses unpredictable, so a write bug is not a reliable control-flow hijack | Any info leak collapses it. 32-bit entropy is brute-forceable if retries are cheap (Shacham et al., CCS 2004). Linux `offset2lib` (2014) showed a fixed executable-to-library delta on PIE. Binosi, Barzasi, Carminati, Polino, and Zanero, ACM CCS 2024 ("The Illusion of Randomness"), found Windows and macOS often randomize executables and libraries less thoroughly than Linux distros, and confirmed the 5.18 entropy drop. The arXiv abstract names "Windows and MacOS" without a version, so "Windows 11" comes from the paper body, not opened in this pass. PaX/grsecurity treated repeated crashes as a signal. Mainline does not |
| **KASLR / KARL / kernel-stack randomization** | PaX **`RANDKSTACK`, Oct 2002**: per-thread kernel *stacks*, not the kernel image. Compile-time `default n`, not a boot-parameter opt-in. **Default-on in 4.12** (2 Jul 2017) unless `nokaslr`. **Not one slide, and this document used to say it was.** `CONFIG_RANDOMIZE_BASE` slides the image. `CONFIG_RANDOMIZE_MEMORY`, in `arch/x86/Kconfig` at **v4.8** (absent at v4.7), `depends on RANDOMIZE_BASE` and `default RANDOMIZE_BASE`, separately randomizes "the base virtual address of kernel memory sections (physical memory mapping, vmalloc & vmemmap)". The help text says the order of allocations is unchanged and, in the optimal configuration, about 30,000 possible virtual addresses per section. So a distro kernel with KASLR on has had four boot-time secrets on x86_64 since before KASLR itself defaulted on, not one. The image slide is still the coarse one. The per-syscall kernel-stack offset landed in **5.13** (2021) as `randomize_kstack_offset=` and `CONFIG_RANDOMIZE_KSTACK_OFFSET_DEFAULT`. The unsuffixed `CONFIG_RANDOMIZE_KSTACK_OFFSET` symbol is **5.18**. Function-granular KASLR was proposed and is not the default | **KARL** (Kernel Address Randomized Link): relink the kernel from a link kit at every boot. Implemented June 2017, shipped in **6.2**. Randomizes *order inside* text and data, which is what a base slide does not do. The booted image is still fixed until the next boot. **6.3** adds a small random gap at the top of thread stacks. That is a few bytes, not KARL | PaX randomized kernel stacks in 2002, and userspace ASLR on PowerPC from 2003. Both dates are Wikipedia's; the Oct 2003 PaX deck the RANDKSTACK claim cites carries no dates at all, and `randkstack.txt` has none.  It did **not** treat image-base KASLR as a serious defense. Interior randomization in this tree is `RANDSTRUCT`, not a KASLR slide. AUTOSLAB is heap isolation, not layout randomization | Stop reliable kernel exploitation that needs absolute kernel addresses | A leaked pointer still retires the region it belongs to. KARL raises the cost of relative assumptions. `nokaslr` remains a one-flag disable on Linux. grsecurity's 2013 post is the right caveat on every "KASLR is enabled" claim in this table |

| **StackGhost** | **OpenBSD 2.8** (1 Dec 2000), SPARC register windows. ### How late, and how completely, the copies arrived

| PaX/grsecurity idea | There | Analogue | Arrived | What was lost in the copy |
|---|---|---|---|---|
| Software NX on IA-32 | 2000 | Linux hardware NX; Windows DEP | 2004 | No NX emulator in mainline. Windows was opt-in for most apps |
| ASLR | 2001 | OpenBSD default; Linux mainline; Windows | 2003 / 2005 / 2007 | Entropy and brute-force reaction were not copied with the idea |
| MPROTECT | 2000 | Linux `PR_SET_MDWE`; Windows ACG | 2023 opt-in; Exploit protection from 1709 (17 Oct 2017), not 2016 | About 20 years, and still not a default. Microsoft gives no single ACG date; the API minimum is Windows 8.1 |
| KERNEXEC | 2003 | SMEP plus a partially read-only kernel | 2011–2017 | The policy was not copied. Read-only text arrived as `STRICT_KERNEL_RWX` |
| UDEREF | ~2006 | Linux SMAP support; hardware around 2014 | kernel 2012 | PaX Team's "six years late" claim. Windows sets the CR4 bit on recent Windows 10/11 and still has no Linux-style policy as of October 2026 |
| REFCOUNT | Dec 2008 | `refcount_t` | 4.11 (2017) | The type was copied, the coverage was not. LWN, 24 Jul 2017: `refcount_t` "initially, protects far less code than the PaX-derived approach." Legacy `atomic_t` remained |
| USERCOPY | Aug 2009 | hardened usercopy | 2016 | Narrower whitelist |
| CONSTIFY | 2009–Nov 2011 | scattered `const`, never comprehensive | — | The maintenance, not the one-time patch, was the contribution |
| STACKLEAK | Apr 2011 | Linux 4.20 | 2018 | Copied, often left compiled out |
| RANDSTRUCT | Jan 2014 | Linux 4.13 plugin | 2017 | Copied, almost never enabled |
| RAP | Oct 2015, public from Apr 2016 | Clang CFI / FineIBT, not RAP | 2018–2023 | Different, narrower, and not a distro default |

Years in the "There" column are the first public patch containing the feature, read off the grsecurity patch archive, except ASLR and MPROTECT, which predate it. Where a mailing-list announcement is later than the patch, the patch date is used.

That pattern is the relationship. PaX shipped a software version of hardware that did not exist yet, and accepted compatibility breaks that a desktop OS with closed drivers and a JIT would not. Mainline later accepted the CPU bit (SMEP, SMAP, CET) or a reduced patch (usercopy, refcount, stackleak, random kmalloc caches), and dropped the part that broke drivers, JITs, or out-of-tree modules. KERNSEAL is the PaX design for sealed kernel storage. The design note is listed, unpublished, from 1 May 2003. AUTOSLAB, introduced in 2020, is an allocation-site isolation defense, and it does not seal pages or remove them from the direct map. **No grsecurity source documents AUTOSLAB as part of KERNSEAL**, so treat the two as neighbouring features rather than one design and a piece of it. Jann Horn's `SLAB_VIRTUAL` is a weaker public version of one piece, virtual non-reuse, and it is not in mainline.

Three earlier internal pointer models are named there: PLUT (256-bit, not thread-safe, no use-after-free detection), SideCaps (thread-safe, but in the author's words "extremely slow": back then Fil-C was 200x slower than normal C), and MonoCaps, before InvisiCaps. **No escape hatch and no `unsafe` keyword** is the design goal. Adoption so far is packaging, not deployment: a rebuilt Linux userland from Linux From Scratch ("Pizlix"), a glibc-based `/opt/fil` distribution, djb's "Filian" which rebuilds Debian packages under a separate architecture triple, and Mikael Brockman's "Filnix" for Nix. **Not a kernel mitigation**: the compiler, the runtime, and the kernel are built with an ordinary compiler, and glibc is shipped recompiled for it. **Costs and limits:** a different ABI, so nothing links against existing objects and everything must be rebuilt; about **4x** in bad cases by the project's own figure, and 1x–4x measured by djb across nearly 9000 crypto microbenchmarks; Linux x86_64 and arm64 only, after Darwin/arm64 and FreeBSD were dropped; a violation is a panic, which is a crash rather than silent corruption. Single active maintainer, no security team, no distribution default. **The name and the "software capability" framing come from the SRI International laboratory that runs CHERI with Cambridge, but no reachable primary source for an SRI project under this name could be opened in this pass** — SRI's project pages no longer resolve and the Wayback Machine has no snapshot — so treat that lineage, and the expansion sometimes given for the name, as unconfirmed |

## 7. What PaX/grsecurity actually was

The 2003 PaX design note already splits exploitation into three levels:

1. Introduce and execute new code.
2. Execute existing code out of the original order.
3. Execute existing code in order, with attacker-controlled data.

PAGEEXEC, SEGMEXEC, and MPROTECT answer the first. ASLR answers the second only probabilistically, and only if the attacker cannot read the layout and cannot retry forever. The project's second decade was the admission that levels two and three live in the kernel: KERNEXEC, UDEREF, USERCOPY, CONSTIFY, REFCOUNT, STACKLEAK, RANDSTRUCT, and finally RAP.

grsecurity owned the surroundings: RBAC, chroot and `/proc` restrictions, ptrace hardening, module-autoload lockdown, and the infoleak closures that make ASLR mean something. Spender's 12 March 2011 post, "The Unseen Benefits of a Security Mindset," is still the best primary document of the lag, and of the habit of copying a feature without copying the upkeep.

Three facts explain the adoption table.

**They shipped software versions of hardware that did not exist yet.** UDEREF is SMAP, six years early, built out of segmentation because there was no CPU bit. KERNEXEC is SMEP plus a policy, before SMEP. MPROTECT is ACG and `PR_SET_MDWE`, a decade or two early. RAP is CET-class CFI without CET. When the hardware arrived, vendors implemented the bit and treated that as the whole job. The policy that made the bit hard to turn off, and the coverage of kernel objects that are not code pages, stayed in the patch.

**They accepted breaks that a product OS will not.** MPROTECT breaks JITs unless the binary is excepted. RANDSTRUCT breaks out-of-tree modules. CONSTIFY breaks drivers that write their own ops tables. A desktop with a plugin ecosystem and a closed-source driver catalog will always choose the opt-in version. That is why Windows ACG, Linux MDWE, and CFG are per process or per binary. OpenBSD could be strict because it controls the userland, and it would rather add an ELF note and a mount option than weaken the default.

**The public patch ended before the upstreaming finished.** On 26 April 2017 the test patches, and all future PaX patches, became non-public. STACKLEAK made it in afterward only because Alexander Popov extracted it from the last 4.9 tarball and spent a year landing it. RAP, UDEREF-as-policy, KERNEXEC-as-policy, and SIZE_OVERFLOW did not. The KERNSEAL design note is listed from 2003 and was never published. AUTOSLAB arrived in the commercial tree in 2020. Neither was in a public tarball. The Kernel Self-Protection Project is the mainstream heir, and it is a subset. The community forks are also subsets:

- **linux-hardened** (Arch, after 2017) is a hardened config plus a small patch set. It is not PaX.
- **Dapper Secure Kernel Patchset** (Matthew Ruffell, 2017–2018) forward-ported the last public grsecurity test patch, **4.9.24**, onto the 4.9 stable series. The latest tagged release is **4.9.135**. From 4.9.75 the maintainer omitted Meltdown, Spectre, and retpoline, and both that note and the 4.9.135 note say to assume those fixes would be months, years, or never. The 4.9.135 note spells retpoline "Reptoline" It is a snapshot of the public patch, not the commercial tree, and it is not a 2026 defense.
So the live descendants in 2026 are a commercial grsecurity tree, a pile of mainline features that are individually weaker, and OpenBSD, which rarely took the code and often took the requirement. Dapper is a stalled 4.9-era port of the last public patch, not a fourth live tree.

OpenBSD's relationship to PaX is parallel invention under a different constraint, not a port. StackGhost (OpenBSD 2.8, December 2000) is earlier than W^X and is not a PaX feature at all, though 2.8's own release page does not list it. OpenBSD's innovations page claims W^X (3.3) and default ASLR (3.4) without attributing them to PaX. Chronologically PaX is first on IA-32 NX (October 2000) and on ASLR (July 2001). OpenBSD is first as a complete operating system that turned the ideas on for every process and then rewrote userland until the breakage stopped. From 2015 onward OpenBSD stopped following. pledge, unveil, KARL, RETGUARD, execute-only mappings, immutable address spaces, and pinsyscalls do not look like PaX features, and none of the other three platforms has the set. The 7.8 and 7.9 releases (2025–2026) are still tightening pledge and closing kernel-address leaks, not adding a new mitigation family. OpenBSD 8.0 is not released as of 16 October 2026. **A correction to an earlier draft:** the claim that the 8.0 release-notes pages 404 was wrong, and wrong twice over. `https://www.openbsd.org/80.html` returns **200** and is a live placeholder reading "Released XXX XX, 2026. (61st OpenBSD release)" and "Artwork by XXX."; the `/8.0.html` form is the one that is not there. The errata page `errata80.html` does read "None yet." The innovations list already tags `getexecpath` (31 Aug 2026) and `rtrd` (16 Sep 2026) for 8.0. Those are not exploit mitigations, and the list does not add a new mitigation family after pinsyscalls and `-fret-clean`.

## 8. Who led, and what is still open

**Historically.** PaX/grsecurity led the technical content from 2000 to about 2015: NX without hardware, ASLR, W^X as a policy, kernel/user separation, copy bounds, structure randomization, stack erasing, and the first serious kernel CFI. OpenBSD led deployment: the first general-purpose OS with stack protectors, W^X, and ASLR on by default, and the only one that kept tightening the default every release instead of adding a sysctl. Windows led productization at scale. DEP, `/GS`, ASLR, CFG, and HVCI reached hundreds of millions of machines, years after the idea, and usually opt-in for anything Microsoft did not itself compile. Linux mainline led almost nothing on this list. It integrated other people's work late, and distributors then chose which symbols to turn on. Android, and later Apple, led the hardware-assisted generation that PaX could not have built in 2001.

**Strongest default in late 2026.** It depends which default is meant.

- **An Apple device with MIE.** iPhone 17 and iPhone Air (A19, 9 September 2025), and **A19 and M5 or later** per the Apple Platform Security guide, whose current edition is dated **August 2026**. That includes M5 Macs. Always-on synchronous enhanced MTE on key attack surfaces, including the kernel, plus typed allocators and tag confidentiality. Nothing else here matches that against memory-corruption exploit chains on those chips. It is not every Apple device. Intel Macs and M1–M4 do not have it. Third-party apps are covered only if the developer opts in.
- **A general-purpose OS with one policy and no hardware lottery.** OpenBSD. Strict W^X, immutable mappings, ASLR, PIE, RETGUARD, execute-only text, pinsyscalls, KARL, pledge, and unveil, applied to the base system rather than to the subset of binaries that remembered the right linker flag. No memory tagging. Ports are less protected than base. Kernel CFI is not RAP. An M5 Mac is a general-purpose computer with stronger memory-safety hardware, and a weaker policy: third-party software is opt-in, and there is no pledge or pinsyscalls equivalent.
- **A corporate desktop, if the machine is a new Windows 11 device and HVCI stayed on.** Microsoft's own documentation says memory integrity is "enabled by default on all new Windows 11 devices." The 1 September 2026 IT Pro post says October 2026 quality updates will enable it on more eligible devices, and turn VBS on where needed, without overriding an existing off choice. The rollout is gradual. Add kernel CFG, kernel CET shadow stacks, PatchGuard, and user CET for Microsoft's own processes. That is a strong kernel. It is not every Windows install. Third-party software is often unprotected. The CR4.SMAP bit is on, on recent Windows 10 x64 and Windows 11. That is not a Linux-style policy, and the hole relative to Linux and OpenBSD on the same Intel CPU is that policy. A high-IRQL exception does not cover the syscall path.
- **A stock Linux server or desktop.** A solid 2010s baseline: NX, ASLR, PIE, **partial** RELRO (full RELRO is opt-in on Debian and Ubuntu, which is what `bindnow => 0` means), strong stack protectors, FORTIFY at level 2 or 3 depending on the distro, KASLR, SMEP, SMAP, KPTI, usercopy, and some init-on-alloc. The gap is exactly where PaX spent its second decade. No default MPROTECT, no default fine-grained CFI, KASLR that is an image slide plus, on x86_64 since 4.8, a separate slide of the direct map, vmalloc and vmemmap, a glibc heap that is merely decent, and user namespaces that add kernel attack surface. Chrome's MiraclePtr is the one software use-after-free quarantine that has actually shipped to ordinary users, and it is not in this kernel. Android's generic kernel plus GrapheneOS is a different Linux, much closer to a productized policy. Commercial grsecurity is still the most complete Linux kernel self-protection stack, and almost nobody is allowed to redistribute the current patch.

**What is still open.** Info leaks and side channels still retire ASLR, and they have started to retire naive MTE. Every deployed CFI scheme is coarse enough that a call to a function of the right type, or a data-only attack, survives. JITs force a hole in W^X on every platform that runs a browser. Linux never grew a default equivalent of pledge plus pinsyscalls plus execute-only libc, and it never grew AUTOSLAB or PRIVATE_KSTACKS. Chrome's MiraclePtr is the software use-after-free quarantine that did ship, and it covers rewritten pointer fields, not the stack and not every pointer. Intel LAM is in the tree from 6.4 and off wherever CPU mitigations are on. Linux 7.2's typed kmalloc partitions are the closest mainline cousin, and they are Clang-only and not per call site. Same-size grooming still works on a stock distro kernel. `LIST_HARDENED` and `io_uring_disabled` exist, and the second still defaults to allowing io_uring. `SLAB_VIRTUAL`, Horn and Rizzo's 2023 proposal, is a weaker public version of one piece of that design: a virtual address is not reused for a different slab cache. It does not isolate per call site, does not seal, and does not hide. It is still not in the mainline hardening config. Userspace CET shadow stacks are opt-in at the kernel level (`CONFIG_X86_USER_SHADOW_STACK` has no default), enabled by some distros such as Ubuntu, and still mostly not enforced at runtime. Hardware mitigations are only as present as the oldest CPU the vendor still supports. Windows sets the CR4.SMAP bit on recent Windows 10 x64 and Windows 11, and still has no Linux-style policy. The 2020 MSRC study said a global clac-by-default enablement was not viable. Microsoft's driver documentation, updated 9 October 2025, still calls that policy a future feature. Yarden Shafir, 16 December 2024, said Microsoft was still working to bring it in. ESET (January 2022) and Connor McGarr (May 2022) disagree on the mechanism of the gap. They agree the syscall path is not the Linux policy. The October 2026 memory-integrity expansion is gradual, and it does not override an existing off choice. Pixel 11 firmware still force-disables MTE as of GrapheneOS's 2 September 2026 update. Speculative-execution mitigations are a treadmill, not a settled control. The capability route is the one that removes the bug class instead of making it harder to exploit, and it is the only such route with a shipping implementation of the whole idea: **Capsicum** put object capabilities into a production kernel in 2010 with no language change and no new hardware, and **FIL-C** now does the same for memory safety by giving C a pointer that is a capability, in a compiler that runs on an ordinary x86-64 or arm64 machine. Neither is a distribution default, and FIL-C is one maintainer's spare-time project, so "the mitigation that actually works" is still a research result in late 2026 rather than something a kernel, a browser or a distro ships. Memory-safe languages are removing code from the problem faster than new mitigations are appearing. The remaining C and C++ in kernels and browsers is still the surface these mechanisms were built for.

PaX defined the problem and the first real answers. OpenBSD is the only project that made those answers, and a second generation of its own, the default for a whole operating system. Windows and Linux shipped the compatible subset. Apple is the first to make hardware memory tagging a **default mitigation for general consumers** rather than a paper, a debug option, or a server-only feature: first on A19 phones, then on M5 and later. SPARC ADI shipped the same mechanism in Solaris 11.3 (announced 26 October 2015) but only on Oracle's own SPARC servers, and never reached the x86 or ARM mass market. The capability tradition is a third line through this document, and it is the one that has never reached a default: Capsicum made object capability a production kernel feature in 2010, CHERI is still research silicon and research kernels, and FIL-C is the software-level version of the same idea running as one person's spare-time compiler. The pattern is the same everywhere else in this document. The ideas that remove the bug class are still research, and the ideas that ship are the ones that make exploitation harder.
